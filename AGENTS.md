## Project Overview

**RacingCoach** is a business automation consulting website specializing in process automation and integration services.

**Tech Stack:**
- Frontend: Next.js 16.2.6 (App Router), React 19.2.4, TypeScript 5, Tailwind CSS 4
- Backend: Node.js API routes, Python automation scripts
- Integrations: Clockify (time tracking), Resend (email)
- Styling: Tailwind CSS 4 with custom color palette (`powder-*`, `dark-blue`)

## Quick Start

```bash
npm run dev          # Development server on http://localhost:3000
npm run build        # Production build
npm start            # Start production server
npm run lint         # Run ESLint
```

- `CLOCKIFY_API_KEY` - Clockify workspace API key (used by `clockify_entry.py`)
- `RESEND_API_KEY` - Resend email service API key
- `RESEND_FROM_EMAIL` - Sender for password reset emails, on a domain verified in Resend (e.g. `Clarivex <no-reply@clarivex.app>`). Defaults to `onboarding@resend.dev`, which only delivers to the Resend account owner

New commands go in as another `.addSubcommand` in `deploy-commands.js` and a branch in `index.js`

- **Bot-only API**: AI features stay in the website and are exposed to the bot under `src/app/api/bot/` (e.g. `POST /api/bot/coach` with `{ discordUserId }`), authenticated with `Authorization: Bearer <BOT_API_SECRET>`. The website and the bot worker must have the same `BOT_API_SECRET`
- **Registering commands**: commands are guild commands in the RacingCoach.app server, so changes show up immediately. After adding, renaming or changing a command in `deploy-commands.js`, run `npm run deploy-commands` from `bot/` locally; Render only runs the bot.

- **Environment variables** (`bot/.env` locally, git-ignored; the worker's Environment in Render):

  - `DATABASE_URL` - Same database as the website

## Telemetry Collector

Like `bot/`, it's not part of the Next.js build (`.dockerignore` excludes it).

- **Uploads**: each saved lap gets a `clientLapId` in `session.json` and is uploaded right after it's saved; `uploaded`/`uploadError` record the result. Played-back `.ibt` files don't upload unless `--upload` is given. Options: `--set-key`, `--no-upload`, `--upload`, `--site <url>` (this run only, e.g. a local dev server), `--no-positions`
- **Track positions (Lat/Lon/Alt)**: iRacing only writes these to its `.ibt` files, never to live telemetry, so live laps are saved and uploaded with empty `Lat`, `Lon`, `Alt` columns first. When live, the collector turns on iRacing's `.ibt` recording (once per connection, so Alt+L to turn it off sticks), and starts it again when the driver has been in the car 5 s with recording turned on but not recording (getting back in the car in the same iRacing session can leave it like that, and the stint would get no `.ibt` file), once per time in the car. When a stint's recording ends (leaving the car, disconnecting, or at the next startup), `IbtEnricher` reads the finished files in `Documents\iRacing\telemetry`, matches each CSV row by `SessionNum`, `SessionTick` and `SessionTime`, fills in the columns and uploads the lap again. File names are `RacingCoach - Driver - Car - Track - 01.50.486 - S0L005.csv` (`S<sessionNum>L<lap>` ID). A lap's CSV is deleted from the PC once it has uploaded and its track positions are settled (`hasPosition`, `positionMissing`, or older than 14 days), so normally just after the stint, once it's re-uploaded with positions; `csvDeleted` in `session.json` records it, and the lap's entry stays for the window's lap list. - **In-Car AI Coach** (`src/lib/inCarCoach.ts`, `src/app/api/collector/in-car-coach/route.ts`, `InCarCoach.cs`): follows the user's own In-Car AI Coach Instructions from the Account page on top of the head coach's AI Coach Instructions. It lists them with `GET /api/collector/laps` and fetches a picked lap's CSV from `GET /api/collector/laps/[id]` (both use the browser sign-in), then analyses it like a dropped CSV. Signing: Azure Artifact Signing, as the organization Clarivex, LLC (SHA-256, timestamped by `http://timestamp.acs.microsoft.com`, as its certificates last 3 days): the workflow runs in the `collector-release` GitHub environment, whose variables (`AZURE_TENANT_ID`, `AZURE_CLIENT_ID`, `AZURE_SUBSCRIPTION_ID`, `ARTIFACT_SIGNING_ENDPOINT`, `ARTIFACT_SIGNING_ACCOUNT`, `ARTIFACT_SIGNING_PROFILE`; no secrets) name the Artifact Signing account and an Entra app registration that trusts that environment's GitHub sign-in (a federated credential, so no password or key exists) and has the Artifact Signing Certificate Profile Signer role. It signs the exe with SignTool and Artifact Signing's plug-in (`Microsoft.Windows.SDK.BuildTools` and `Microsoft.ArtifactSigning.Client` from NuGet), ISCC signs the uninstaller and the installer with the same command (`/DSignTool`, and `signcheck` refuses an unsigned exe), and nothing is published unless both files' signatures verify, are timestamped and are from `SIGNING_PUBLISHER` (Clarivex, LLC). It signs in to Azure just before signing and fetches the code signing token at once, as GitHub's sign-in token lasts minutes. Inno Setup is pinned (`INNO_SETUP_VERSION`, 6.7.3, downloaded from its GitHub release and checked to be signed by Pyrsys B.V.): 7.x changes what sign tools are given. The publisher name must stay the same: the collector's updater (`Authenticode.cs`) only runs a download whose valid signature is from the same organization as the running collector's (no check when the running one isn't signed, e.g. a local build or one before 1.40.0), and SmartScreen's reputation builds on the signer, so signed releases warn less over time, though new ones can still warn at first. The Account page's Download button (`src/components/CollectorKeyCard.tsx`) links to `releases/latest/download/RacingCoach.Collector.Setup.exe`; the plain exe stays in each release for running without installing and for collectors that aren't installed to update themselves. The collector updates itself: at startup `UpdateCheck.cs` finds a newer release on GitHub, `SelfUpdater.cs` downloads its exe beside the running one (`.new`, checked against the size GitHub lists) and the banner offers Restart Now; otherwise it installs when the window closes, after the last laps are saved. Installing renames the running exe to `.old` (a running exe can be renamed, not overwritten) and moves the new one into place; Restart Now starts it with `--after-update`, which waits up to 60 s for the old one to release the single-instance mutex. The next start deletes `.old` and any half-finished `.download`. An installed collector can't write its own folder (`SelfUpdater.UsesInstaller`), so it downloads the release's installer to the temp folder instead and, on Restart Now or close, runs it with `/SILENT /SUPPRESSMSGBOXES /NORESTART /UPDATE=1` (plus `/LAUNCH=1` for Restart Now); Windows asks to allow it, and the installer waits up to 60 s for the collector's single-instance mutex to go before replacing the exe. Keep the installer's `AppId` unchanged, or Windows treats a new version as a second app. Builds that aren't the single-file exe (`dotnet run`), failed downloads and failed installs fall back to the banner's Download button (the release page). Collectors before 1.2.0 only show the banner. Bump `<Version>` in the `.csproj` to match when tagging, for local builds

## Troubleshooting

**npm run dev fails with "command not found"?**
- Ensure Node.js 18+ is installed
- Run `npm install` first
- Check that `.env.local` exists (can be empty initially)

**ESLint errors on import statements?**
- Verify TypeScript path aliases in `tsconfig.json` (e.g., `@/*` → `src/*`)
- Run `npm run lint -- --fix` to auto-fix common issues

**Build succeeds but `npm start` is slow?**
- Normal for first cold start
- Production bundle includes optimizations
- Subsequent requests are faster
